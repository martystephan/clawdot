# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What Clawdot Is

The mobile-first IDE for agentic coding. A CLI daemon on the user's own machine hosts terminal sessions running AI coding agents; a phone connects to it through an end-to-end encrypted relay (paired via QR code) that only forwards ciphertext. The long-term differentiator is **generative test surfaces**: tunneled live web previews for web apps, declaratively-assembled API test panels for backends.

**Agents run as terminal sessions, not via an agent protocol.** A previous iteration integrated agents via ACP (Agent Client Protocol) with `agent.*`/`session.*` events and a durable per-session event log; that whole layer was deliberately removed — the product is terminal-first now. Agents are just commands (`claude`, `codex`, …) running in daemon-side PTYs. Don't reintroduce agent-protocol coupling or a session/event-log layer in the daemon.

Status: early development. Working vertical slice: the daemon (WebSocket, port 8787) drives real PTYs (`@lydell/node-pty`, prebuilt — no native compile) via `terminal.*` protocol messages; the web app renders them with xterm.js. Two lifetimes: the header-button right panel is an ephemeral connection-scoped shell (PTY killed when the connection drops), while **terminal sessions** (sidebar "New terminal") are persistent daemon-scoped PTYs running a configured agent command (`claude`, `codex`, …) full-screen in the main view — they survive disconnects/reloads, and reattach replays a serialized snapshot from a daemon-side headless xterm (`@xterm/headless` + serialize addon; raw byte-log replay renders redraws as duplicated lines — don't regress to it). They do NOT survive a daemon restart (a PTY cannot be rehydrated). The agent command list lives in config.json (`terminalAgents`) and is editable from the app's settings dialog via `settings.get`/`settings.update` (the remotely-editable config subset — relay/port stay local-only). The daemon also tracks workspaces (project directories, `workspaces.json` under the data dir — `--data-dir` / `CLAWDOT_DATA_DIR`, default `~/.clawdot`) and serves `fs.list`/`fs.mkdir` for the phone's workspace picker.

Remote access works end to end: the daemon dials out to a self-hosted relay (`apps/relay`; NO built-in default endpoint — `--relay <url>` is persisted to the data dir's `config.json`, `CLAWDOT_RELAY` env applies per run, `--no-relay` disables, `--relay ""` forgets; never hardcode a relay/domain anywhere, users host their own) and each remote client is a multiplexed channel on that one socket, E2E-encrypted with an X25519 handshake + ChaCha20-Poly1305 counter-nonce framing (`packages/protocol/src/tunnel.ts`, exported as `@clawdot/protocol/tunnel`). `clawdot pair` mints a one-time ticket over the LOCAL socket only (privilege split: remote clients must never mint tickets) and prints a QR linking to the relay-hosted web app with the ticket in the URL fragment; after first contact the device's static key is the credential (`~/.clawdot/identity.json` = daemon identity — never regenerate over it; `devices.json` = trusted device registry). The relay never parses payloads — it forwards opaque frames between a daemon socket (4-byte channel-id prefix) and bare client sockets, and any feature needing plaintext belongs in daemon or client, never the relay. The relay also serves the built web app (`--static`, SPA fallback) so the QR pairing link works; it deploys as ONE container from the root `Dockerfile` (builds the whole monorepo in-image, healthcheck on `/healthz`) — the user runs it on their VPS via Dokploy (Dockerfile build, domain → port 9700, Traefik does TLS); the Dockerfile is the only supported deployment path, and its ENV declarations are the relay's runtime-config reference (overridable in Dokploy's Environment tab). The first surface exists: the **web preview panel** renders a dev server from the daemon's machine inside the app. All preview traffic rides the existing connection as `preview.*` messages (so it's E2E-encrypted for free and the relay stays a dumb pipe): a service worker (`apps/web/public/preview-sw.js`, plain JS, no build step) intercepts preview requests and hands each to the app window over a MessageChannel; the page bridge (`apps/web/src/features/preview/bridge.ts`, wired in `use-daemon.ts`) sends `preview.fetch` and streams the response back. The SW runs in one of two modes decided by its own hostname: **origin mode** (preferred) serves previews on a subdomain — the relay's static hosting is deliberately Host-agnostic, so a DNS record + proxy route is all the infra — where EVERY path proxies to the previewed port, so previewed apps see real URL paths (client routers/pushState/SSR hydration work) and get storage separate from the IDE; since that SW can't message the app window (different origin), a hidden companion iframe (`__clawdot/preview-bridge.html`, embedded by the preview panel) registers the SW there and relays its messages to the app bridge over a MessagePort. Two subdomain shapes, probed concurrently by the panel (timeout → auto-fallback): `preview.<app-host>` (RECOMMENDED — one ordinary DNS record + ordinary Let's Encrypt cert; wildcard certs need DNS-API challenges, so don't steer users there; the hostname can't carry the port, so the companion supplies it via `?port=` — pushed to the SW after registration, re-queried after SW restarts, and injected into preview HTML as `window.__clawdotPreviewPort` for the ws shim) and `p<port>.<app-host>` (wildcard DNS, per-port storage isolation). **Path mode** (`/preview/<port>/` on the app origin, with referrer/clientId fallbacks for absolute-path subresources) remains the fallback for the Tauri shell (bundle origin, no subdomains) and hosts without wildcard DNS — its known limit is that pages can read the path prefix in location.pathname, breaking client-side routers; the daemon (`apps/cli/src/preview.ts`, per-connection `PreviewProxy`) fetches from loopback (127.0.0.1, falling back to ::1 — `localhost`-bound dev servers like Vite on macOS are often v6-only) and strips framing/frame-blocking headers (content-length/-encoding, CSP, x-frame-options). The SW also intercepts cross-origin requests FROM preview pages: loopback targets (a frontend calling `http://localhost:8000`) always tunnel to that port — on the phone they'd hit nothing — and hosts on the user's settings allowlist (`previewAllowedHosts` in config.json, edited in the settings dialog, bridge↔SW via push + on-demand query) tunnel by absolute URL, which sidesteps CORS entirely (the daemon fetches server-to-server, the SW synthesizes the response, no browser CORS check ever runs). The allowlist check lives daemon-side (`PreviewProxy.targets`) and is the security boundary keeping the daemon a port forwarder rather than an open proxy a malicious previewed page could SSRF through — never serve an absolute-url fetch without it. Service workers can't intercept WebSockets, so the SW injects `__clawdot/ws-shim.js` into preview HTML documents, which replaces `window.WebSocket` and bridges sockets to the parent window via postMessage → `preview.ws.*` — this is what makes Vite HMR work; the shim tunnels loopback-targeted sockets to their port the same way (sockets to external hosts stay native — not allowlist-tunneled). Cookie-session apps work via a daemon-side jar (`apps/cli/src/cookies.ts`): SW-constructed Responses can't set cookies in the browser, so the daemon captures `set-cookie` from tunneled responses and replays `cookie` on later requests (HTTP + WS handshakes) — in-memory only (NEVER persist it), daemon-scoped (per-connection would log users out on every phone screen-lock), and strictly origin-keyed so loopback ports and allowlisted hosts can never see each other's sessions. Known v1 limits: per-connection in-flight ownership (a dropped connection aborts its requests/sockets), external-host WebSockets are never tunneled. Not yet built: generative test surfaces (API test panels). See the README roadmap for build order.

## Commands

pnpm 11 workspace, Node >= 20, ESM throughout (`"type": "module"` everywhere).

```sh
pnpm install
pnpm build        # builds all packages recursively
pnpm dev          # the whole dev environment, one command (see below)
pnpm typecheck    # tsc --noEmit across all packages
pnpm lint         # currently aliased to typecheck — no ESLint configured yet
```

**Dev loop:** `pnpm dev` at the root runs every package in watch mode AND starts a development daemon: the cli `dev` script is `tsx watch src/index.ts serve --port 8788 --data-dir .dev-data --no-relay`, and `daemonUrl()` in the web app connects to port 8788 when served by Vite (`import.meta.env.DEV` — stripped from production builds, which keep 8787/relay behavior). So one command gives a working stack at `http://localhost:5173` that is fully isolated from an installed `clawdot service` daemon: different port, throwaway `.dev-data/` dir (gitignored), no relay, and it never touches `~/.clawdot` (config, identity, workspaces). Don't "fix" the dev scripts to share the real port or data dir. Caveat: a remote link stored in the dev origin's localStorage (from testing pairing at localhost:5173) takes precedence over the direct connection — unpair in the UI to get back to the dev daemon.

Per-package (e.g. `pnpm --filter @clawdot/cli dev`):

- `@clawdot/protocol` — source-only internal package: `exports` point straight at `src/*.ts`, there is NO build step and no `dist/`. Every consumer compiles it itself (tsx for cli/relay dev, Vite for web, tsup `noExternal` bundling for the cli/relay production builds), so there is no build-order or watcher dependency anywhere — don't reintroduce one by pointing its exports at built output.
- `@clawdot/cli` — `tsup` build, `dev` runs the dev daemon (see above), `start` runs `dist/index.js`; bin name is `clawdot`. `@clawdot/protocol` is deliberately a devDependency bundled into dist via tsup `noExternal` so the package installs standalone (`npm i -g ./apps/cli`, later npm publish) — don't move it back to dependencies. Subcommands: `serve`, `service` (background service: install/update/uninstall/restart/status — launchd on macOS, systemd user unit on Linux, Startup-folder launcher + hidden cmd supervisor loop on Windows; `detectService` also catches Linux without a systemd user manager, e.g. WSL), `setup` (wizard — detects the platform and offers the matching service install at the end), `config`, `pair`, `devices`, `help`; bare `clawdot` opens the interactive menu (`src/menu.ts` — setup wizard on first run, never starts the daemon unless the user picks it; non-TTY prints help instead) — interactive ones use `@clack/prompts` and share helpers in `src/cli-ui.ts` + `src/daemon-client.ts` (request/response over the local socket). Daemon settings (relayUrl, port, terminalAgents) persist in the data dir's `config.json` via `ConfigStore`; flags > env > config.json. `device.list`/`device.revoke` protocol messages are local-socket-only, like `pair.start`.
- `@clawdot/web` — Vite; `dev`/`build`/`preview`. Also hosts the **Tauri 2 mobile shell** (`src-tauri/`): `pnpm tauri ios dev "<simulator name>"` builds and runs on the iOS simulator, `tauri android init` generates the Android project once an SDK exists (none installed yet). The shell wraps the same frontend (`frontendDist: ../dist`); in dev it starts its OWN Vite on port 1430 (`beforeDevCommand`) so it never clashes with the root `pnpm dev` Vite on 5173 — don't merge those. Inside Tauri the page origin is the app bundle, so `daemonUrl()` returns null when `__TAURI_INTERNALS__` is present (relay/pairing is the only path) and pairing uses the paste-code dialog (QR deep links don't open the shell). `gen/apple` is committed (regenerable but holds signing/config edits); `src-tauri/target/` and `gen/schemas/` are gitignored. The transitive `time` crate is pinned to 0.3.47 in `src-tauri/Cargo.lock` — 0.3.48 breaks `cookie`/`tauri-utils` with E0119 conflicting-impl errors; re-pin after any `cargo update`. Device deploys/`ios build` need `bundle > iOS > developmentTeam` in `tauri.conf.json` (simulator runs don't).
- `@clawdot/relay` — `tsup` build bundling ALL deps into one `dist/index.js` (deploys as a single file); bin name is `clawdot-relay`

Tests (cli and relay e2e run their own `dist/` — build those first; protocol needs no build):

- `pnpm --filter @clawdot/protocol test` — tunnel crypto unit tests (handshake, tamper/replay/MITM rejection) via `tsx --test` against `src/`
- `pnpm --filter @clawdot/relay test` — relay e2e: fake daemon + clients doing the real E2E handshake through a real relay socket
- `pnpm --filter @clawdot/cli test` — daemon e2e (`test/e2e.mjs`: workspaces, fs browsing, ephemeral + persistent terminals, settings, restart persistence), then remote-access e2e (`test/relay-e2e.mjs`: relay + daemon + paired "phone" doing a full terminal round trip through the tunnel). No real agent binary needed — terminals run plain shell commands.

**No build order in dev:** `@clawdot/protocol` is consumed from source (see above), so `pnpm dev` straight after `pnpm install` just works — no prior `pnpm build` needed, and protocol schema changes hot-reload (Vite HMR in web, tsx watch restarts the daemon).

## Architecture

Protocol-first monorepo — clients are just renderers, so new surfaces (desktop app, VS Code fork) plug into the same backbone later:

```
apps/
  web/        → React 19 + Vite — the IDE UI (later wrapped with Tauri for native mobile)
  cli/        → Node daemon — hosts terminal sessions (PTYs), workspaces, pairing
packages/
  protocol/   → shared message schemas (Zod), E2E crypto helpers, protocol versioning
```

Key design rules from the README that should shape any implementation work:

- **Message flow:** the protocol separates `terminal.*` messages (PTY lifecycle, keystrokes, raw output) from `surface.*` events (things the client renders — web previews, test panels). Adding a new widget type must never require touching the transport layer.
- **Terminal sessions are daemon-scoped, with one viewer at a time.** The agent process lives on the daemon, not the connection — phones disconnect constantly. Persistent PTYs feed a daemon-side headless xterm; reattach replays a serialized screen snapshot (ordered strictly: `terminal.attached`, snapshot, live tail). Exactly one connection views a terminal at a time (concurrent viewers would fight over the PTY size): an attach while another device is viewing answers `terminal.busy`, and `takeover: true` moves the view here while the kicked viewer gets `terminal.busy` (the web app shows "open on another device" + a take-over button for both). Ephemeral panel shells die with their connection so a vanished phone never leaks processes.
- **The relay is a dumb, self-hostable pipe.** It forwards ciphertext only — no code, prompts, or keys ever reach it in plaintext.
- **Protocol over platform.** Every client speaks the same schema-validated (Zod) protocol; the UI is replaceable, the backbone isn't.

## Conventions

- Strict TypeScript via the root `tsconfig.json` (all packages extend it): `strict`, `noUncheckedIndexedAccess`, `noUnusedLocals/Parameters`, and `verbatimModuleSyntax` — use `import type` for type-only imports.
- Dependency hygiene is strict: no hoisting, and pnpm build scripts are blocked except for allowlisted packages (`allowBuilds` in `pnpm-workspace.yaml`).
